For a Mac-first app, I’d build the interface in SwiftUI and keep the TypeScript calculator for the first release. Swift Charts and Table cover the two views that need the most custom drawing and interaction work in GPUIX. The contribution rules are the part worth sharing across clients.

SwiftUI versus GPUIX on the Mac

For this calculator I’d choose SwiftUI. Someone editing a contribution spends most of their time entering numbers, picking dates, checking a particular year, and moving between fields. SwiftUI has controls for each of those tasks. GPUIX’s strongest advantage here is that a Svelte developer can take the existing TypeScript rules and timing parser straight into the desktop app.

The form control Swift doesn’t give you

“Every 15th for 10 years starting in 2028” is part of this app’s language. A date picker can choose a day. It takes the calculator’s parser to turn that sentence into a monthly rule, anchor it to the projection start, and set its end year. I’d keep the parser shared, show its interpretation below the field, and use the existing parser tests as the contract for any Swift replacement. If a native text-editing requirement exceeds SwiftUI’s controls, a single field can host an AppKit view through NSViewRepresentable. Timing grammar · Parser cases · AppKit integration

A Swift interface now, a decision on the engine later

My choice while the web app and CLI are active: write the Mac views in Swift and keep one TypeScript implementation of projections, recurrence parsing, and revision-checked edits. I tested this boundary. A short Swift program changed the roth amount from $500 to $600 in a copy of the example, called the existing Bun CLI, and decoded both results. The 20-year baseline moved from $688,986 to $729,567. Current CLI

The test launched a process per calculation using the locally installed runtime. For a shipped app, I’d bundle a helper with a small versioned JSON interface, keep it running, and send committed changes asynchronously. Both the Mac app and MCP can call the same edit implementation. The extra costs are packaging and signing the helper, handling restarts, and discarding stale replies if a newer edit finishes first. GPUIX can import the engine directly.

If the Mac app becomes the primary product: put the calculator, rule parser, and edit commands in a Swift package shared by the app and a small stdio MCP executable. The official Swift MCP SDK supports that arrangement. An all-Swift build removes the helper process, but leaves the existing web and CLI clients on TypeScript unless you migrate them too. Before switching engines, compare monthly steps and annual totals on shared JSON fixtures, including leap years, start/end placement, salary bases, disabled rules, and flat versus percentage growth. Keep rounding at the same points as the current engine. Swift MCP SDK · Projection rules

The deciding test

Enter a recurring salary contribution by keyboard, clear and retype its amount, change its end date, then save. Select a year in the table and inspect the contributions behind it. Run the same edit through MCP and compare the result. The native rendering and Swift-to-CLI experiments establish the pieces. That workflow would establish whether they fit together well enough to ship.

What ports to GPUIX

GPUIX runs Svelte components against a native element tree. Runes, snippets, and component composition still fit. A Svelte component that calls browser APIs or expects HTML elements inherits a porting job along with its markup. I’d add apps/desktop with its own entry point and keep the existing web app as the behavioral reference. Renderer overview

Calculator and rules
Import @retirement/calculator for variance scenarios, salary rules, timing, growth, and step details. The CLI already uses it headlessly. Extract the chart’s annual-series mapping and currency formatters for both clients. Keep the same fixtures and unit tests. Calculator exports

Rebuild field views with the toolkit’s TextField, Select, Dialog, and Button. The current shadcn-svelte wrappers depend on HTML, Bits UI, and Tailwind. The route currently seeds defaults in a SvelteKit server load, initializes Superforms, then hydrates from browser local storage. Desktop needs a startup loader and a durable scenario store. How I’d draw the GPUIX chart

Build one ProjectionPlot. Today LayerChart draws the axes, area, and tooltip, while the Svelte component chooses the annual balances and optionally adds two variance series. That division gives the native component a small input: years and up to three balances per year. Current chart

Keep the geometry in TypeScript

The experiment mapped 20 annual values to pixel coordinates, generated SVG paths, and stacked five native layers: grid, area fill, upper line, lower line, and baseline. GPUIX tints each <svg source={markup}> as a mask, so each color gets a layer. Native text provides the axis labels and selected value. For smooth curves, the existing D3 shape generator can return path strings directly. This use of D3 needs no browser element. Toolkit SVG implementation · D3 line generator

Give the plot one input target

I read the plot’s window coordinates from onlayout and mapped horizontal pointer position to the nearest year. In both native runs, clicking the first year selected 2026, pressing Right advanced to 2027, and clicking the far edge selected 2045. Selection only changes the readout. It can also drive a crosshair and a shared highlight in the table. Native hit-testing tools

The experiment used a fixed viewport, fixed scale, solid fill, and straight segments. For the app, derive the scale from all visible series, handle a single year and a flat zero balance, and recalculate the plot bounds on resize. Test scrolling, high-DPI rendering, and keyboard focus at both edges. Keep the yearly table available for exact values.

Give agents the same edit as the app

An MCP server is worth building even if the desktop prototype ends here. A useful first interaction is “What if I raise my monthly Roth contribution by $100?” The agent should locate the rule by ID, preview the change against the saved plan, and be able to save that exact edit when asked.

Why the form cannot own agent edits

I disabled the 401k rule in a copy of the CLI example and passed it through the web form’s conversion functions. The conversion dropped enabled: false and changed salaryBasis from perContribution to monthly. The projected final balance moved from $401,900 to $689,813 without an intentional financial edit. A domain command should touch only the fields it names. Form conversions · Domain types

I’d put runtime config validation, edit commands, and revision handling in a shared TypeScript package. A desktop form and a local retirement-mcp process call it independently. The MCP client starts the server over stdio, so agents can use a saved scenario with the window closed. Reserve stdout for protocol traffic and send diagnostics to stderr. MCP transports

A small first tool set

list_scenarios and get_scenario
List IDs, names, and revisions. Fetch one scenario’s assumptions and rule IDs on demand. Constrain lookup to the app’s scenario store.
preview_change
Accept a scenario ID, base revision, and typed operations. Validate the resulting config, then return the normalized edits, before/after totals, and a preview ID. Include units in the schema: an annual return of 5% is 0.05 in the engine, whereas a salary contribution of 6% uses 6. A preview leaves the saved plan intact.
apply_change
Save the exact preview against its base revision in one transaction. Return the new revision. A repeated request for the same preview returns its recorded result. If a person edited the plan since preview, return a conflict with the latest revision. The agent can fetch and preview again. MCP tool schemas and results

What an agent could show you

For the example above, set_flat_contribution_amount on rule roth sets its monthly amount to $600. At the 5% baseline, the extra $24,000 contributed over 20 years adds $40,580 to the projected balance, including $16,580 in additional growth. A client can show those figures and the one-field diff before saving. Deltas use full precision before rounding.

I’d store versioned config JSON and a revision number in SQLite. Both processes can use a conditional update in one transaction, including edit history for undo. On window focus or a revision notification, the desktop app reloads committed data and preserves any in-progress draft for conflict review. Enforce unique rule IDs, valid dates, rate units, and timing combinations at the shared boundary. Keep detailed step logs opt-in so a simple preview returns only the numbers requested.

When to commit to GPUIX

  1. Ship a lossless edit through the shared package. Use the CLI example to prove a $500 → $600 edit changes only roth.amount. Add a case with a disabled rule and a nondefault salary basis. A stale preview must leave the newer revision intact.
  2. Try the whole edit loop in one native window. Load the plan, change an amount, save, and see the chart and table update. Apply another edit through MCP and check that the window reflects it. Repeat with the daily-compounding fixture. Compare the figures with the CLI and exercise the custom timing editor by keyboard. Daily example
  3. Make one distributable build. The Mac used here has Node 24.13 and Bun 1.3.8. Node ran the experiment. Upstream calls for Bun 1.4+ to build a distributable, and its Svelte custom renderer ships with a pinned Svelte build. Isolate that toolchain in the desktop workspace. Test a packaged launch on a clean target machine before promising support. Runtime and platform matrix · Packaging and signing

My decision gate is the custom contribution editor. I’d continue with GPUIX if a user can enter a recurring rule, correct an invalid date, save with the keyboard, and hear the resulting value with VoiceOver. GPUIX documents gaps in live announcements, described-by relationships, and modal focus semantics. Test those in a real window. If that workflow takes too much platform-specific work, the web UI can still use the shared edit model, and the MCP server keeps its value. Accessibility support
